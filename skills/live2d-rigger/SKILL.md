---
name: live2d-rigger
description: Create and rig an editable Live2D character from a brief, through complete layered artwork, native compilation and motion review.
---

Default workflow: the user describes the character they want; you generate complete separate artwork parts with the host's native image tools, rig them, build, show motion, and the user only reports issues they see, which you then fix (one targeted repair at a time). Early in that flow, get the official free Live2D sample models as structure references: call live2d_reference_samples; if the ones you need are not present, tell the user plainly what you will download (which samples, from Live2D's own sample-data site, into this plugin's data folder), show the licence links it returns, and only after the user agrees call live2d_fetch_reference_sample with accept_licence=true, one sample at a time. Reuse samples that are already present. Study them with live2d_reference_samples (sample_id) and live2d_inspect_resources/live2d_check_motion for part split, parameters, physics, expressions and motion groups. Use them only as structural references; never copy their artwork into the user's model and never redistribute them. Read [the references page](../../llmwiki/references.md).

Read the [bundled wiki](../../llmwiki/index.md), especially its production guide, before choosing tools. Ask for character identity/reference, intended expressions/motion, target Cubism/Core version, editable-source deliverables and actual authoring resources. A reference portrait is not a set of complete riggable parts.

The task guide's sections on the complete-part contract, rig recipe, adaptive build route and Core motion review are binding. Use live2d_begin_model to retain the brief/resources. Design complete RGBA parts in the MAIN session, including backing hidden by the neutral pose; import reviewed parts with live2d_model_layer. Use live2d_model_rig with source="prototype-roll" for the built-in experimental recipe, or author a custom rig against the selected producer’s actual API. Select a real native compiler/editor export path with explicit {project}/{output}; live2d_build_model requires a native MOC3 package. live2d_render_model_motion uses a real selected SDK/Core renderer and requires decodable video. Diagnostics are live2d_inspect_resources, live2d_check_motion and live2d_reference_samples. Do not call an agent launcher a compiler. Missing native authoring capability blocks compilation, not design or source preparation.

Review neutral identity, deformation extremes, occlusion, seams, expression return and motion using the actual target Core. Keep authored layers/rig, runtime package, any native editable document and reviewed motion together. A MOC3 signature or decoded video proves neither a sound rig nor visual acceptance. No automatic corrective generations, physical camera, tracking or VTS changes.

Start from the user's intended result. Reuse known resource choices; ask missing questions only in ordinary chat. Establish hardware, available local/remote tools, subscriptions versus verified API entitlements, privacy, acceptable waiting time and maximum API spend (zero is valid). Prefer free paths that meet quality needs. A subscription does not prove API access. Save non-secret choices in the private task, never credentials. Do not silently install/download, upload private inputs, switch providers or spend money. Reason/write in the active host; no secondary reasoning API or agent worker. Images are inspected/generated/edited directly in the MAIN session using native tools. Preserve accepted work, pauses and original inputs. Publishing requires separate explicit authorization.

When the user already has a character (a .model3.json): call live2d_open_model with the ABSOLUTE path of the .model3.json or its folder (if the user names a relative folder, run pwd in the terminal and join them; the tool does not resolve relative names) (it works on a copy; the original is never changed), then live2d_inspect_model to explain in plain words how she is put together (separate parts, controls, expressions, what makes hair and skirt swing), and live2d_render_clip to show her moving (its measured_movement lists what really moved; describe the clip only from that, never from guesses). To fix a plain-words issue such as "her hair barely moves when she turns", call live2d_adjust_physics on the copy (output_scale and follow_through raise how far and how long loose parts swing; groups picks which), render the same clip again, and compare the before and after frames yourself in the main session before saying what changed. Say plainly that the change is on the copy and what it does not change (art, shapes, the compiled model). If live2d_open_model reports the renderer is not ready, say what is missing instead of guessing. Never describe a clip you have not looked at.

To give an existing character more life (she stands stiff, she barely moves): render her current Idle motion first with live2d_render_clip (motion = its Idle name from live2d_inspect_model), look at the contact sheet, then write a better one with live2d_write_motion (a few sine and blink tracks and eased key tracks on her real parameters: breathing, body sway, head angle X/Y/Z, eyes, blinks; parameter ids and ranges come from live2d_inspect_model) and, if loose parts should follow, live2d_adjust_physics. Render the new motion with the same view and length and compare the two contact sheets before you say what changed.

When you show a clip, say in plain words what she does in it and that it is ready to watch; do not print file paths in your answer unless the user asks where the files are.

Make a new idle read clearly at small video size, loop cleanly (use 8 seconds, whole sine cycles) and still look natural: breathing over the full 0 to 1 range (2 cycles), a head turn of about 18 to 22 degrees to each side with eased key tracks and holds, the eyes following the turn (about 0.6), a small nod and tilt (4 to 6 degrees), body sway of about 4 to 5 degrees, two blinks, a little skirt sway; then live2d_adjust_physics with output_scale about 2.5 and follow_through about 1.5 so the hair follows. Check the result with live2d_render_clip and its measured_movement; if it is still subtle, enlarge the motion and render again before answering.

The built-in Umamo layer transport also has a static-only mode: call live2d_model_rig with no source, then live2d_build_model with no command_argv after importing complete reviewed layers in back-to-front order. It needs the user-configured JDK and Umamo classpaths documented in the task guide. It does not produce a rig, controls, physics, an animated character, or proof of visual quality. Never describe a static export as animated.

For each individually generated complete part, ask for it alone with hidden backing on a flat pure magenta background, no shadow, checkerboard or text; choose pure green if the part contains magenta. If the host exposes a real transparent-background option, use it. Otherwise import the opaque PNG with live2d_model_layer key_color=[] for corner detection (or an RGB triple), then inspect its returned before/after preview in the main session. The conservative cutout refuses non-flat borders and broad ambiguous key-colour bands, but cannot prove hidden backing or detect every ambiguous edge: inspect the complete part and scale against the design. Preserve the original image and placement.

Clearly key-coloured areas, including enclosed holes, are removed and tinted orange in the preview. Never use the key colour in the artwork itself; review the tinted regions. Do not automatically regenerate: state the visible defect and correction, then allow at most one targeted redo per part.

If a user says a part is too big, too small, in the wrong place or covers another, use live2d_place_layer to adjust its position and scale on the common canvas without changing its art; rebuild and render the same view for comparison. The static adapter remains static.

Before each layer import inspect the whole part and its hidden backing, then pass complete_part=true only if it is an independently painted complete part. The flag records an attestation, not automated proof. Do not attest a sliced flat portrait.

For new parts, prefer the host image tool's reference-image EDIT mode: use the approved full-figure reference as the input and ask it to keep only the named complete part in its exact original canvas position, complete hidden backing, and paint everything else flat magenta. Request the same canvas dimensions and position, no shadow or text. Review every whole part and its alpha; do not treat algebraically cut portrait slices as complete backing. Import a genuinely aligned full-canvas result with aligned_to_reference=true. If an image edit drifts or resizes the part, do not claim it is aligned. For unrelated cropped parts without a reference, the plugin proposes coarse role-based placement from the face bounds; inspect the composite and refine it with a plain-words nudge. Reference matching is a verifier with a strict confidence gate, not proof of identity or alignment.

For a built-in experimental prototype with a reported hair-root or crown geometry issue, inspect the matching poses and, after an actual authoring-recipe fix, use live2d_rebuild_prototype to retain the earlier build and render the same motion again. Physics-strength changes cannot fix a disconnected crown. Compare the actual frames and do not claim a fix from a successful rebuild alone.

The experimental source="prototype-roll" recipe supplies partial roll, sway, breath, blink, approximate gaze, mouth opening and hair physics when matching parts exist. It does not supply XY head turns or independent limbs and requires actual Core and visual review.
